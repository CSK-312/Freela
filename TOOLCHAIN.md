# Reproducible Noir toolchain

The tested presentation toolchain is pinned to:

- Nargo / Noir: `1.0.0-beta.26`
- Barretenberg: `5.2.0`
- Proof system: UltraHonk

These exact versions compiled, proved, and verified this repository on 2 November 2026 under Ubuntu in WSL, and natively on macOS (Apple Silicon).

## Install (macOS, Linux, or Ubuntu in WSL)

```sh
curl -L https://raw.githubusercontent.com/noir-lang/noirup/main/install | bash
~/.nargo/bin/noirup --version 1.0.0-beta.26

curl -L https://raw.githubusercontent.com/AztecProtocol/aztec-packages/refs/heads/next/barretenberg/bbup/install | bash
~/.bb/bbup -v 5.2.0
```

Confirm versions:

```sh
~/.nargo/bin/nargo --version
~/.bb/bb --version
```

## Run circuit tests

`python3 generate_circuit.py` regenerates both circuits. Then, from `circuit/`:

```sh
~/.nargo/bin/nargo test
```

The full Python suite (including a real prove/verify run when both tools are installed):

```sh
python -B -m unittest discover -s tests -v
```

## Application integration

When Flask runs on Windows, `zk_engine.py` discovers these binaries in the configured WSL distribution (`Ubuntu` by default), converts the project path to its `/mnt/<drive>/...` form, and runs the pinned toolchain there. Override the distribution with `FREELA_WSL_DISTRO`. Native installations can be selected with `NARGO_BIN` and `BB_BIN`.

The application checks both versions before compiling. It does not fall back to a simulated proof: missing or incompatible tools produce an explicit error instead of a false verified result.

## Credentials and proofs

There are two Noir packages, generated by `generate_circuit.py` from one shared commitment function:

- `circuit_commit/`: the issuer runs it with `nargo execute` to compute a Pedersen commitment over a freelancer's full job history, their account id and a random secret salt. The result is stored in the `credentials` table. A new version is issued whenever a client approves and reviews one of their jobs.
- `circuit/`: the eligibility proof. Private inputs are the history arrays and salt; public inputs are the job's four thresholds, the job id, the applicant id and the commitment. It checks that the history hashes to the commitment, then checks the thresholds.

On the first application the app compiles both packages and pins the verification key (its SHA-256 is stored with each application). Every proof runs in its own folder under `.local/zk-runs/`, is verified against the pinned key, and its decoded public inputs must equal this job's thresholds, this applicant and their current commitment.

A freelancer's first application issues their initial credential automatically. To issue credentials for all existing freelancers up front:

```sh
python zk_engine.py issue-missing
```

Trust model: the platform holds the history and the salt, so it is the credential issuer. Clients only ever see that a proof verified. History edited or dropped after issuance can no longer produce a valid proof.
